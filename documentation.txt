==============================================================================
DOCUMENTATION TECHNIQUE - PROJET DJANGO / ANGULAR / GRAPHQL
==============================================================================

Bienvenue sur le projet ! 
Cette documentation détaille le workflow standard pour ajouter une nouvelle fonctionnalité (Module/Entité) en respectant l'architecture "Modulaire & Scalable".

PRÉ-REQUIS
----------
- Backend : Python 3.10+, Django, Graphene
- Frontend : Node 18+, Angular 18+, Apollo GraphQL
- Outils : Script `./snake` (Wrapper manage.py)

==============================================================================
0. ARBORESCENCE & GUIDAGE RAPIDE (LA CARTE)
==============================================================================

Pour vous repérer rapidement : L'architecture est symétrique (Backend <-> Frontend).

.
├── apps/                     # BACKEND : Modules Métier (Django)
│   ├── core/                 # FRAMEWORK INTERNE (Ne pas toucher sauf expert)
│   │   ├── api/controllers/  # RouterController, BaseController
│   │   ├── services/         # BaseService (Logique CRUD universelle)
│   │   └── management/       # Scripts Seeds & Scaffolding
│   └── <module>/             # VOS FONCTIONNALITÉS (Students, HR...)
│       ├── models/           # Structure de données
│       ├── services/         # Surcharge de la logique (before_save...)
│       └── graphql/          # API de Lecture (Queries)
│
├── frontend/                 # FRONTEND : Application Angular
│   ├── src/app/core/         # FRAMEWORK FRONT
│   │   ├── abstracts/        # BaseListComponent, BaseFormComponent
│   │   └── routing/          # DynamicRouter, Routes Enum
│   ├── src/app/shared/       # UI KIT (Table, Modal, Input, Skeleton...)
│   └── src/app/features/     # ÉCRANS MÉTIER (Miroir de apps/)
│
└── snake                     # CHEF D'ORCHESTRE (Lance tout le reste)

GUIDE DE SURVIE (TROUBLESHOOTING)
---------------------------------
1. "Page Blanche / Spinner infini" ?
   -> Vérifiez si le Backend tourne (`./snake run`).
   -> Regardez la console Navigateur (F12) : Erreur 0 ou Connection Refused confirme que le back est éteint.

2. "Erreur CORS / Status 0" ?
   -> Le Backend est éteint. Ce n'est pas une vraie erreur CORS.

3. "Je ne vois pas ma nouvelle page" ?
   -> Avez-vous lancé `./snake seed:navigation` ?
   -> Avez-vous ajouté la route dans `component.registry.ts` ?

4. "Mon champ ne s'enregistre pas" ?
   -> Vérifiez le `Serializer` (Backend) ou le `FormGroup` (Frontend).

WORKFLOW DE DÉVELOPPEMENT (ÉTAPE PAR ÉTAPE)
==============================================================================

1. BACKEND : SCAFFOLDING & MODÉLISATION
---------------------------------------
L'outil `snake` permet de générer la structure de base.

a) Générer les fichiers Backend
   Commande : ./snake craft scaffold <NomEntite> <NomApp>
   Exemple  : ./snake craft scaffold Evenement profilmanagement

b) Définir le Modèle
   Fichier : apps/<app>/models/<entite>.py
   Action  : Ajoutez vos champs (CharField, DateTimeField, etc.).

c) CORRECTION CRITIQUE : IMPLÉMENTER LA PAGINATION
   Le scaffold génère par défaut une requête "Liste simple". Pour les listes paginées du frontend, il faut modifier la Query.
   
   Fichier : apps/<app>/graphql/Queries/<entite>_query.py
   
   Modèle à suivre :
   ------------------------------------------------------------
   from apps.core.graphql.Types.paginated_type import get_paginated_type
   
   <Entite>PaginatedType = get_paginated_type(<Entite>Type)

   class <Entite>Query(graphene.ObjectType):
       <entites> = graphene.Field(
           <Entite>PaginatedType,
           search=graphene.String(),
           page=graphene.Int(default_value=1),
           page_size=graphene.Int(default_value=10)
       )

       def resolve_<entites>(root, info, search=None, page=1, page_size=10, **kwargs):
           queryset = <Entite>.objects.filter(is_deleted=False).order_by('-created_at')
           
           if search:
               queryset = queryset.filter(Q(nom__icontains=search)) # Adapter le filtre

           # Utilisation de l'utilitaire de pagination (DRY)
           from apps.core.utils.pagination import paginate_queryset
           paginated_data = paginate_queryset(queryset, page, page_size)

           return <Entite>PaginatedType(**paginated_data)
   ------------------------------------------------------------

d) Migrations
   Commande : ./snake craft automigrate

e) Configuration du Menu (Navigation)
   Ne PAS utiliser de script temporaire.
   Fichier : apps/core/management/commands/seed_navigation.py
   Action  : Ajoutez votre page dans la structure MODULE_STRUCTURE.
   Commande : ./snake seed_navigation (ou python3 manage.py seed_navigation)

2. FRONTEND : GRAPHQL & CODEGEN
-------------------------------
Nous n'écrivons PAS de requêtes GraphQL "en dur" (inline) dans les composants. Nous utilisons la génération de code.

a) Définir la Query
   Fichier : frontend/src/app/features/<module>/graphql/<module>.graphql (Ex: structure.graphql)
   Action  : Ajoutez les Fragments et les Queries (GetById et GetAll).
   Règle   : Utilisez UN SEUL fichier par module (ex: structure.graphql pour tout le module structure).
   
   Exemple :
   query GetAllEvenements($search: String, $page: Int, $pageSize: Int) {
     evenements(...) { ... }
   }

b) Générer le code TypeScript
   Le générateur a besoin d'un Token JWT valide pour l'introspection.
   
   1. Récupérer un Token (si besoin, via script ou login).
   2. Lancer la génération :
      export JWT_TOKEN="<votre_token>" && npm run codegen
      (vous pouvez utiliser la commande ./snake updategql)
    Résultat : Les types TypeScript généraux sont créés dans `frontend/src/app/graphql/types.ts` et les services GQL Angular spécifiques à chaque module sont générés à côté des fichiers `.graphql` correspondants (ex: `frontend/src/app/features/hr/graphql/hr.generated.ts` grâce au preset `near-operation-file`).

------------------------------------------------------------------------------

3. FRONTEND : COMPOSANTS SERVICIELS
-----------------------------------

a) Service Angular
   Créez un service qui étend `BaseService` et injecte le service généré par Codegen. Notez que la lecture de liste s'effectue via GraphQL (les routes CUD classiques n'exposent pas directement d'endpoint REST `list` sans méthode). Si vous devez interroger une liste, surchargez `list()` dans le service pour appeler le service GQL, ou utilisez la Query GraphQL directement dans votre composant.
   
   Fichier : frontend/src/app/features/<module>/services/<entite>.service.ts
   Exemple :
   ------------------------------------------------------------
   @Injectable({ providedIn: 'root' })
   export class EvenementService extends BaseService {
     endpoint = 'evenement';
     private generatedGQL = inject(GetAllEvenementsGQL); // Généré par Codegen

     getQuery() {
       return this.generatedGQL.document;
     }
   }
   ------------------------------------------------------------

b) Composant Liste
   Créez le composant qui étend `BaseListComponent`.
   
   Fichier : frontend/src/app/features/<module>/components/<entite>-list/...
   Exemple :
   ------------------------------------------------------------
   export class EvenementListComponent extends BaseListComponent<any> {
     service = inject(EvenementService);
     query = this.service.getQuery(); // Récupération propre de la query
     responseKey = 'evenements';
     // ...
   }
   ------------------------------------------------------------

c) Enregistrement de la Route
   Fichier : frontend/src/app/core/routing/component.registry.ts
   Action  : Mappez l'URL (définie dans seed_navigation) vers le composant lazy-loaded.

4. FRONTEND : STANDARDISATION UI & MODALES
------------------------------------------
Pour garantir une interface cohérente et un code maintenable, nous utilisons des composants partagés.

a) Listes Standardisées
   Utilisez `<app-ui-list-page>` dans votre template.
   
   Exemple (HTML) :
   ------------------------------------------------------------
   <app-ui-list-page title="Titre" [isLoading]="..." [isEmpty]="...">
     <ng-container header-actions>...</ng-container>
     <ng-container table>
       <app-ui-table [columns]="tableColumns" ...></app-ui-table>
     </ng-container>
     <ng-container pagination>...</ng-container>
   </app-ui-list-page>
   ------------------------------------------------------------

   Côté TypeScript, étendez `BaseModalListComponent<T>` pour bénéficier de la gestion automatique des modales (Create/Edit/Delete/Details).

b) Formulaires & Modales
   Ne créez pas de pages dédiées pour les formulaires simples/moyens. Utilisez des modales.
   
   1. Créez un composant Form (ex: `VoitureFormComponent`) qui étend `BaseFormComponent`.
   2. Utilisez `<app-ui-form>` et `<app-ui-input>` pour une UI standard.
   3. Intégrez ce formulaire dans la liste via `<app-ui-modal>` et `<ng-container [ngSwitch]="modalMode()">`.

   Exemple d'intégration (Liste HTML) :
   ------------------------------------------------------------
   <app-ui-modal [isOpen]="isModalOpen()" (close)="closeModal()">
     <ng-container [ngSwitch]="modalMode()">
        <!-- Suppression -->
        <app-ui-confirm-modal *ngSwitchCase="'delete'" ...></app-ui-confirm-modal>
        
        <!-- Formulaire (Création/Édition) -->
        <app-voiture-form *ngSwitchDefault 
            [item]="selectedItem()" 
            (cancel)="closeModal()" 
            (success)="onSave()">
        </app-voiture-form>
     </ng-container>
   </app-ui-modal>
   ------------------------------------------------------------

6. FORMULAIRES COMPLEXES (CAS D'ÉTUDE : PERSONNE)
--------------------------------------------------
Pour des entités avec relations (1-N) ou beaucoup de champs, suivez ce pattern (ex: Personne + Contacts).

a) Frontend : Architecture du Formulaire
   - **Tabs** : Utilisez `<app-ui-tabs>` pour organiser les champs.
   - **FormArray** : Pour les relations 1-N (Contacts), utilisez un `FormArray`.
   - **UX Validation** :
     - Activez le bouton Submit en permanence : `[disableInvalid]="false"`.
     - Surchargez `onSubmit()` pour vérifier la validité :
       * Si invalide : Affichez un Toast warning + Changez d'onglet automatiquement vers l'erreur.
       * Si valide : Appelez `super.submit()` ou `save()`.

   Exemple (PersonneFormComponent) :
   ------------------------------------------------------------
   override ngOnInit() {
       super.ngOnInit(); // CRITIQUE pour les logs
   }

   onSubmit() {
       if (this.form.valid) {
           this.save().subscribe(...);
       } else {
           // Logique custom : Switch tab si erreur dans les contacts
           if (this.contactsArray.invalid) {
               this.activeTab = 'contacts';
               this.toastService.warning('Veuillez corriger les contacts.');
           }
           this.form.markAllAsTouched();
       }
   }
   ------------------------------------------------------------

b) Backend : Nested Writes (Écritures Imbriquées)
   L'architecture supporte la création/modification d'enfants via le parent.

   Fichier : apps/<app>/api/serializers/<entite>_serializer.py
   Action  : Déclarez le serializer enfant.

   Exemple :
   ------------------------------------------------------------
   class PersonneSerializer(BaseSerializer):
       # Nested Write activé par BaseSerializer
       contacts = ContactSerializer(many=True, required=False)

       class Meta:
           model = Personne
           fields = '__all__'
   ------------------------------------------------------------
   
   Note : Contrairement à l'automatisme complet, les écritures imbriquées (Nested Writes) nécessitent d'appeler explicitement la méthode helper `create_nested(self, parent_instance, relation_name, data_list)` de `BaseSerializer` dans le cycle de sauvegarde de vos serializers spécifiques.

7. INFRASTRUCTURE AS CODE & COMMANDES DE MANAGEMENT (APPS/CORE/MANAGEMENT)
==============================================================================
Le projet suit une philosophie "Infrastructure as Code" pour la donnée de configuration.
Le dossier `apps/core/management/commands` contient les scripts qui définissent l'état du système.

a) Scaffolding (craft.py)
   ----------------------
   Générateur de code pour accélérer le développement.
   Commande : `./snake craft scaffold <Modele> <App>`
   - Crée le Model, Service, Serializer, Controller, Type, Query, Mutation.
   - Met à jour `schema.py` et `apps.py`.

b) Navigation & Menu (seed_navigation.py)
   --------------------------------------
   Définit la structure du menu (Modules > Pages) et les liens.
   - Éditez `MODULE_STRUCTURE` dans ce fichier.
   - Appliquez : `./snake seed:navigation` ou `python3 manage.py seed_navigation`.
   - C'est la source de vérité pour le Frontend (DynamicRouter) et la génération de routes.

c) Permissions & Accès (seed_access.py)
   ------------------------------------
   Définit toutes les permissions du système.
   - Liste les "Resources" (ex: "student", "user") et les "Actions" (create, read, update, delete).
   - Appliquez : `./snake seed:access`.
   - Génère les entrées dans la table `Access` utilisées par le système de Rôle.

d) Rôles par Défaut (seed_roles.py)
   --------------------------------
   Configure les rôles initiaux (Admin, Manager, etc.) et leur associe les permissions définies dans `seed_access`.
   - Appliquez : `./snake seed:roles`.
   
e) Génération Frontend (start_generate_routes.py)
   ----------------------------------------------
   Lit la configuration de `seed_navigation.py` et génère le fichier TypeScript `routes.enum.ts`.
   - Appliquez : `./snake updategql` (qui lance cette commande en interne).

f) Données de Démonstration (seed_data.py)
   ---------------------------------------
   Peuple la base avec des données fictives pour le dev (Etablissement, Users).

> BUNDLE : La commande `./snake config-server` ou `seed:all` lance ces seeds dans le bon ordre.

8. FONCTIONNALITÉS AVANCÉES DU FRONTEND
==============================================================================
L'architecture Frontend est le miroir du Backend, conçue pour l'extensibilité.

a) Routing Dynamique (Database Driven Menu)
   ----------------------------------------
   Le fichier `app.routes.ts` ne contient que les routes statiques (Login, 404).
   Les modules métiers sont chargés dynamiquement depuis la base de données.
   
   1. Backend : `seed_navigation.py` définit la structure (Module -> Pages -> Lien).
   2. Frontend : `DynamicRouterService` (APP_INITIALIZER) :
      - Appelle l'API GraphQL `GetAllPages`.
      - Mappe chaque lien (ex: `/students`) vers un composant via `COMPONENT_REGISTRY`.
      - Injecte les routes dans Angular au démarrage.
   
   > Pour ajouter une page : Ajoutez l'entrée dans `seed_navigation.py` (Backend) ET dans `component.registry.ts` (Frontend).

   PRO-TIP : Sécurité & Typage
   ---------------------------
   - ROUTING TYPÉ : Ne jamais utiliser de chaînes (ex: '/users'). Utilisez l'Enum généré `AppRoutes.USER`.
     Commande : `./snake updategql` génère `routes.enum.ts` automatiquement.
   
   - SAFE MODE : Si le Backend (Menu API) échoue, `DynamicRouterService` charge automatiquement des routes de secours (définies dans `FALLBACK_ROUTES`) pour ne pas bloquer l'application.

b) Réactivité Globale (StructureStateService)
   ------------------------------------------
   L'application est Multi-Etablissement native.
   - `StructureStateService` utilise un SIGNAL Angular (`currentEstablishmentId`).
   - `BaseListComponent` écoute ce signal via un `effect()`.
   - Résultat : Changer d'établissement dans la Navbar recharge AUTOMATIQUEMENT toutes les listes ouvertes sans rechargement de page.

c) BaseListComponent : L'Usine à Listes
   ------------------------------------
   Ne réinventez pas la roue pour chaque liste. Héritez de `BaseListComponent`.
   Elle fournit gratuitement :
   - Pagination (synchro avec Backend).
   - Filtrage (via `initFilterForm`).
   - Export Excel & PDF (Bouton natif qui exporte TOUTE la liste filtrée, pas juste la page courante).
   - Gestion du chargement (`isLoading`) et des états vides.

9. GESTION DES FICHIERS (GED CENTRALISÉE)
==============================================================================
Le projet utilise un module `apps/documents` qui agit comme une GED transverse.
Au lieu de champs `FileField` éparpillés sur chaque modèle, nous utilisons une relation polymorphique.

a) Architecture (Back)
   -------------------
   - Modèle Unique : `apps.documents.models.Document`.
   - Polymorphisme : Utilise `GenericForeignKey` pour s'attacher à n'importe quelle entité (Student, Employee...).
   - Stockage : Dossier `/media/` (Non versionné). Organisé par identifiant de tenant et type de média : `media/<hub_id>/<establishment_id>/<category>/<filename>`.

b) Upload (Front & Back)
   ---------------------
   Le `DocumentService` simplifie l'upload en résolvant le ContentType automatiquement.
   
   Endpoint : `/api/document/create/` (POST Multipart)
   Payload : 
   - `file`: (Le binaire)
   - `content_type_app`: "students" (Nom de l'app Django)
   - `content_type_model`: "student" (Nom du modèle en minuscule)
   - `object_id`: "123" (ID de l'entité parente)
   - `document_type`: "PHOTO" | "CV" | "AUTRE"...

   > Note : C'est géré automatiquement si vous utilisez le pattern `FormData` standardisé dans les formulaires complexes.

c) Sécurité & .gitignore
   ---------------------
   Le dossier `media/` contient les données utilisateurs. Il est EXCLU du Git via `.gitignore`.
   Ne jamais commiter de fichiers dans ce dossier.

10. ARCHITECTURE DE CONNECTIVITÉ DU LANCEUR (TAURI <=> DJANGO BRIDGE)
==============================================================================
Lorsque le projet est exécuté au sein du Hub Ethernanos, l'application Django 
communique de façon bidirectionnelle et sécurisée avec le lanceur de bureau Tauri.

a) Lancement de l'Application et Injection Stdin
   ----------------------------------------------
   Tauri (Rust) orchestre le démarrage de Django via `app_manager_service.rs` :
   1. Allocation de Port Dynamique : Tauri cherche un port libre de manière séquentielle 
      à partir du port par défaut de l'application (`port` à `port + 100`).
   2. Injection de Configuration : Tauri écrit un payload JSON directement sur l'entrée 
      standard (`stdin`) du processus enfant Django.
      Ce payload contient :
      - `session_token` : Jeton dynamique unique généré via Sha256 de `hub_pid:timestamp`.
      - `tenant_id` : L'identifiant de l'établissement / tenant courant.
      - `app_port` : Le port de routage alloué.
      - `db_config` : Les configurations et identifiants de la base de données.
      - `hub_api_key` : Clé d'API globale partagée.
      - `admin_pass` : Le mot de passe par défaut administrateur.
      - `url_prefix` : Le préfixe URL de routage de type `/schoolmanage/{tenant_id}/`.
      - `cloud_api_url` : L'URL de synchronisation cloud.
   3. Django (`manage.py`) capture cette configuration au démarrage via la détection de 
      l'environnement `ETHER_HUB_PID`, lit `stdin` et configure dynamiquement les variables 
      d'environnement (comme `DATABASE_URL` et `ETHER_APP_PREFIX`) avant de démarrer le serveur.

b) Poignée de Main Sécurisée (Hub Handshake)
   -----------------------------------------
   Pour garantir qu'aucun client externe non autorisé ne puisse interroger l'application 
   hébergée localement, le middleware `HubHandshakeMiddleware` applique un bouclier strict :
   1. Validation de Jeton : Toute requête REST (`/api/*`) ou GraphQL (`/graphql`) doit 
      transmettre l'en-tête `X-Hub-Session-Token` correspondant exactement à 
      `ETHER_SESSION_TOKEN` (le jeton envoyé par Tauri via stdin).
   2. Exceptions Publiques : Les requêtes d'authentification initiale (`/api/auth/login/`) 
      et l'accès direct Django Admin (`/admin/`) contournent cette restriction pour permettre 
      l'initialisation et la maintenance.
   3. Immunité CSRF : La validation réussie du jeton de session Hub active l'exemption CSRF 
      adaptative (`_dont_enforce_csrf_checks = True`) pour simplifier les requêtes API/GraphQL 
      derrière le WebView2 (qui bloque fréquemment les cookies tiers).

c) Nettoyage des Préfixes Dynamiques (Routing)
   -------------------------------------------
   Le middleware `HubPrefixMiddleware` synchronise le chemin de routage interne de Django :
   1. Détection de Préfixe : Si le préfixe configuré (`ETHER_APP_PREFIX`, ex : `/schoolmanage/test/`) 
      est détecté en tête de l'URL (`request.path_info`).
   2. Nettoyage : Il extrait ce préfixe pour ne présenter au Resolver Django que la route 
      métier propre (ex : `/schoolmanage/test/api/login` devient `/api/login`).
   3. Synchronisation : Le middleware synchronise `SCRIPT_NAME` de l'environnement WSGI avec le 
      préfixe afin de préserver la génération correcte des URLs absolues.

d) Signal de Disponibilité (Handshake de démarrage)
   ------------------------------------------------
   - Au démarrage, après exécution des migrations et configuration de Waitress, le serveur 
     Django imprime sur son flux standard `stdout` le jeton de synchronisation `[HUB_SIGNAL:READY]`.
   - Tauri intercepte cette ligne dans sa boucle asynchrone Rust et déclenche l'événement global 
     `app-ready` vers l'interface utilisateur frontend du lanceur, lui indiquant de charger 
     l'application Webview en toute sécurité.

e) Variables d'Environnement Clés (Bridge)
   ---------------------------------------
   Le pont d'intégration utilise des variables d'environnement clés pour configurer et sécuriser le runtime :
   - `ETHER_HUB_PID` : Identifiant de processus (PID) de Tauri. Sa présence active le mode Hub dans l'application Django.
   - `ETHER_SESSION_TOKEN` : Jeton de session dynamique unique utilisé par le middleware pour authentifier chaque requête entrante.
   - `ETHER_APP_PORT` : Port TCP sur lequel le serveur WSGI Waitress écoute.
   - `ETHER_HUB_API_KEY` : Clé d'API globale partagée permettant d'autoriser l'accès aux points d'entrée `/api/external/*`.
   - `ETHER_TENANT_ID` : Identifiant unique de l'établissement / tenant courant.
   - `ETHER_APP_PREFIX` : Préfixe d'URL dynamique (ex: `/schoolmanage/{tenant_id}/`) utilisé par le middleware de routage.
   - `ADMIN_DEFAULT_PASSWORD` : Mot de passe par défaut pour le compte administrateur créé à l'initialisation.
   - `DATABASE_URL` : Chaîne de connexion injectée dynamiquement selon la configuration de la base de données (PostgreSQL ou SQLite).
   - `LC_ALL`, `LC_MESSAGES`, `LANG` : Forcées à "C" au niveau du processus Django pour éviter les problèmes d'encodage lors des retours d'erreurs PostgreSQL localisés.

11. PROCÉDURE EN CAS DE CHANGEMENT DE VPS (MIGRATION DE DISTRIBUTION)
==============================================================================
Si vous devez migrer le serveur de mise à jour et de distribution des modules 
vers un nouveau VPS, suivez scrupuleusement la procédure suivante :

a) Mise à jour DNS
   ---------------
   1. Connectez-vous à votre registrar de domaine (ex: Cloudflare, Namecheap...).
   2. Modifiez l'enregistrement DNS de type A pour le sous-domaine de distribution :
      - Nom : `updates.ethernanos.space` (ou le nom configuré dans `nginx.conf`)
      - Nouvelle Valeur : L'adresse IP publique de votre nouveau VPS.
      - TTL : Positionnez-le au plus bas (ex: 2 min / 120s) pour accélérer la propagation.

b) Configuration de Nginx sur le nouveau VPS
   ------------------------------------------
   1. Installez Nginx sur le nouveau serveur :
      `sudo apt update && sudo apt install nginx`
    2. Créez ou copiez la configuration de serveur Nginx pour le sous-domaine de mise à jour (ex: `frontend/nginx.conf` ou un fichier Nginx personnalisé) :
       `sudo nano /etc/nginx/sites-available/updates.ethernanos`
    3. Ajustez les chemins absolus (comme la racine de stockage des fichiers de release `/home/stech/launcher/releases/`) et les directives de reverse proxy.
   4. Activez la configuration en créant le lien symbolique :
      `sudo ln -s /etc/nginx/sites-available/updates.ethernanos /etc/nginx/sites-enabled/`
   5. Testez la syntaxe Nginx et rechargez le service :
      `sudo nginx -t && sudo systemctl reload nginx`

c) Génération du Certificat SSL
   ----------------------------
   Le Hub requiert impérativement des connexions sécurisées HTTPS.
   1. Installez Certbot et son plugin Nginx :
      `sudo apt install certbot python3-certbot-nginx`
   2. Générez le certificat SSL de type Let's Encrypt :
      `sudo certbot --nginx -d updates.ethernanos.space`
   3. Vérifiez que le renouvellement automatique est configuré :
      `sudo systemctl status certbot.timer`

d) Migration des Fichiers et Permissions
   -------------------------------------
   1. Recréez la structure de dossiers sur le nouveau VPS (ex: `/home/<user>/launcher/releases/`).
   2. Transférez les fichiers de mise à jour existants (`metadata.json`, fichiers `.tar.gz`, 
      exécutables `.exe`, `.dmg`, `.deb`...) de l'ancien serveur vers le nouveau.
   3. Assurez-vous des permissions de lecture pour que Nginx puisse servir les fichiers :
      `chmod -R 755 /home/<user>/launcher/releases/`

12. SYNCHRONISATION HYBRIDE (CLOUD <-> LOCAL) MULTI-TENANT
==============================================================================
Le système permet une synchronisation bidirectionnelle (JSON + Fichiers Médias)
entre les instances Locales (déployées dans les écoles via le Hub) et l'instance Cloud (VPS).

L'architecture est orchestrée par le Frontend Angular (Hub) qui agit comme un pont :
- Le serveur Local et le Cloud ne communiquent jamais directement.
- Le Hub (Angular) consomme les API des deux serveurs et transfère les données.

a) Synchronisation des Données (JSON)
   ----------------------------------
   Fichier Backend : `apps/core/api/views/sync.py`
   - InitialSyncView (Cloud -> Local) : Génère l'arbre complet des données (Pull).
   - SyncInView (Local) : Ingère l'arbre de données complet.
   - SyncDeltaView (Local -> Cloud) : Expose les modifications locales (Deltas).
   - PushDeltaView (Cloud) : Reçoit et intègre les Deltas locaux.

b) Synchronisation des Fichiers Binaires (Images, Documents)
   ---------------------------------------------------------
   Fichier Backend : `apps/core/api/views/sync_assets.py`
   - AssetManifestView : Liste tous les fichiers d'un établissement avec leur Hash MD5.
     Le filtrage est STRICTEMENT multi-tenant : l'API filtre tout avec `establishment=est`,
     garantissant qu'un tenant (ex: École A) ne télécharge que SES fichiers (logos, 
     photos de profil de son personnel, documents liés, etc.).
   - AssetTransferView : Gère l'upload et le download granulaire des fichiers binaires.

c) Le Pont Frontend (Le Chef d'Orchestre)
   --------------------------------------
   Fichier Frontend (Hub) : `ui/src/app/core/services/hub/hub-sync.service.ts`
   - executeDeepSync() : Point d'entrée.
   - pushSync() / pullSync() : Gèrent l'échange JSON.
   - syncAssets() : Compare les deux Manifestes MD5 (Local vs Cloud). Si une différence 
     est détectée (fichier manquant ou modifié), le Hub télécharge l'image depuis la source 
     et l'upload vers la destination (via des requêtes POST/GET multipart).
